# EDA (Exploratory Data Analysis)

Exploratory Data Analysis is the step where you find out what the data actually
is, as opposed to what the documentation claims it is. It sits between data
collection and cleaning, and its output is a set of *decisions*, not a set of
charts.

For the surrounding process see
[01.Data Science Process.md](01.Data Science Process.md).

## The five activities

1. **Understanding the Data**: examine structure, types and overall characteristics.
2. **Data Quality**: missing values, duplicates and inconsistencies.
3. **Distribution & Outliers**: shape, spread, skew, extremes.
4. **Relationships**: correlation, association, group differences.
5. **Feature Engineering**: what the findings imply for the model.

Activities 1-2 are mandatory and quick. Activities 3-4 are where the findings
live. Activity 5 overlaps step 5 of the process - it is listed here because EDA
decides which features are worth building.

## What EDA is for

| Purpose | Example from this repo |
| --- | --- |
| Find data-quality bugs | `cleaned_data.csv` still has a `NaN` in `country` |
| Find a bug *before* the cleaning | `raw_data.csv` mean age is 32.75 pre-dedup, 33.29 post-dedup |
| Identify informative missingness | 125 of 177 missing `Age` values are non-survivors |
| Quantify imbalance | `Survived` is 61.62 / 38.38 |
| Find redundant columns | `petal_length` and `petal_width` correlate at 0.963 |
| Find the target variable | `globalAirQuality.csv` has `aqi`; the IRIS file has `species` |
| Test assumptions | Is `Fare` normal? No - 116 points above the IQR fence |
| Decide transformations | `Fare` needs `log1p`, not scaling |

## What EDA is not

- **Not a data-cleaning step.** Do not `fillna` during EDA. You will choose a fill
  strategy before you know the distribution.
- **Not model fitting.** EDA answers "what is in the data", not "what predicts the
  target". Hold the target mostly in reserve; look at it deliberately, in one or
  two places, not casually against every column.
- **Not a report for stakeholders.** It is a working document. A chart you looked
  at once and learned nothing from was still worth the two minutes.

## 1. Understanding the Data

### The nine questions

Before touching a single value, answer these:

1. How many rows and columns?
2. What are the column names, and what do they mean?
3. What is the dtype of each column?
4. Is the primary key unique?
5. How many missing values per column?
6. How many distinct values per column?
7. Is the target present, and what is its class balance?
8. Is the data cross-sectional, longitudinal, or time series?
9. Does the shape match what the documentation promised?

### The API map

Print these once per dataset and read the output carefully.

```python
import pandas as pd

df = pd.read_csv("IRIS.csv")

df.shape          # (150, 5)         - rows, columns
df.columns        # Index([...])      - names
df.dtypes         # dtype per column
df.head()         # first 5 rows
df.tail()         # last 5 rows
df.info()         # dtypes + non-null counts + memory
df.describe()     # count/mean/std/min/quartiles/max
df.nunique()      # distinct values per column
df.sample(5)      # random 5 rows
df.memory_usage(deep=True)
```

`describe()` gives quantiles, not just the mean and standard deviation - and the
quartiles are where skew shows up. For Iris:


Read `petal_length`: mean 3.758 but median 4.350, min 1.0, max 6.9. The mean sits
*below* the median in a dataset whose minimum is far from its maximum - that is
left skew, and it is visible in three numbers.

### A compact profiling helper

Worth writing once, reusing on every dataset:

```python
def profile(df: pd.DataFrame, name: str = "dataset") -> pd.DataFrame:
    rows = []
    for col in df.columns:
        s = df[col]
        rows.append({
            "column": col,
            "dtype": str(s.dtype),
            "non_null": int(s.notna().sum()),
            "null": int(s.isna().sum()),
            "null_pct": round(s.isna().mean() * 100, 2),
            "nunique": int(s.nunique()),
            "sample": str(s.dropna().iloc[0])[:20] if s.notna().any() else None,
        })
    out = pd.DataFrame(rows)
    print(f"--- {name}: {df.shape[0]} rows x {df.shape[1]} cols ---")
    return out


profile(pd.read_csv("Titanic-Dataset.csv"), "Titanic")
profile(pd.read_csv("globalAirQuality.csv"), "AirQuality")
```

This one table answers questions 3, 5, 6 and 9 at once, and it is the artefact you
paste into an EDA report.

### dtypes tell you what went wrong

```python
t = pd.read_csv("Titanic-Dataset.csv")
print(t.dtypes)
# PassengerId      int64
# Survived         int64
# Pclass           int64
# Name             str
# Sex              str
# Age           float64     <- float only because of NaN
# SibSp            int64
# Parch            int64
# Ticket           str
# Fare          float64     <- float only because of NaN
# Cabin            str
# Embarked          str

a = pd.read_csv("globalAirQuality.csv")
print(a["timestamp"].dtype)    # str  <- a bug, not a feature
```

Two lessons:

- A numeric column that is `float64` when it should be `int64` is telling you it
  has missing values, not that it needs decimals.
- A timestamp that arrived as `str` is the most common silent problem in tabular
  work. It cannot be resampled, and `min() < max()` on strings only works by
  accident when the format is ISO-8601.

```python
a["timestamp"] = pd.to_datetime(a["timestamp"])
print(a["timestamp"].dtype)    # datetime64[us]
print(a["timestamp"].min(), "->", a["timestamp"].max())
# 2025-11-04 18:25:17.554219 -> 2025-11-19 17:25:17.554219
```

### Identify the target and its balance

| Dataset | Target | Type | Balance |
| --- | --- | --- | --- |
| `Titanic-Dataset.csv` | `Survived` | binary | 549 died / 342 survived = 61.62 / 38.38 |
| `IRIS.csv` | `species` | 3-class | 50 / 50 / 50 |
| `globalAirQuality.csv` | `aqi` | continuous | mean 104.65, median 103.00 |
| `raw_data.csv` | `income` | continuous | mean 57600, median 56500 |

```python
t = pd.read_csv("Titanic-Dataset.csv")
print(t["Survived"].value_counts())
# 0    549
# 1    342
print(t["Survived"].value_counts(normalize=True).round(4))
# 0    0.6162
# 1    0.3838
```

That 61.62 / 38.38 split decides the rest of the project: stratified splits, and
AUC rather than accuracy as the metric.

### Data structure

`describe()` and `info()` will not tell you this. Ask directly.

```python
a = pd.read_csv("globalAirQuality.csv", parse_dates=["timestamp"])

print("rows:", len(a))
print("cities:", a["city"].nunique(), "countries:", a["country"].nunique())
print("rows per city:", a.groupby("city").size().unique())    # [360]
print("time span (days):", (a["timestamp"].max() - a["timestamp"].min()).days + 1)  # 16

# Wide or long?
print(a.shape)   # (18000, 15) - wide: one row per city-hour, pollutants in columns
```

50 cities x 360 hourly readings = 18000. It is a **panel**: repeated measurements
per city over time. That tells you immediately that a random train/test split is
wrong, that the same city's readings are not independent, and that "which city has
the worst air" and "how does a city's air change" are two different questions
requiring two different methods.

### Key uniqueness

```python
print(t["PassengerId"].is_unique)          # True
print(pd.read_csv("raw_data.csv")["id"].is_unique)   # False - id=1 appears twice
```

A non-unique primary key means the table is either one-to-many (a fact table
needing a join) or genuinely dirty. `raw_data.csv` is the second case, and it is
covered in [section 2](#2-data-quality).
