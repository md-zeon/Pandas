# Data Science Process

## The eight steps

1. Define the Problem
2. Data Collection
3. EDA
4. Data Cleaning & Pre-processing
5. Feature Engineering
6. Modeling
7. Evaluation
8. Deployment

## The process is a loop, not a line

The list above reads like a checklist, and that is exactly how it gets misused. In
practice you cycle through it repeatedly:

```
Define -> Collect -> EDA -> Clean -> Engineer -> Model -> Evaluate
   ^                                                      |
   |________________________  findings  _________________|
```

Two concrete reasons for the loop:

- **EDA routinely invalidates the problem statement.** You assume a data-quality
  problem is a modelling problem, then discover in step 6 that the label column is
  measured after the outcome. You go back to step 1.
- **Evaluation routinely invalidates the features.** A model trains at 0.95 AUC and
  scores 0.58 on holdout. Step 5 leaked information into the features; you go back
  and rebuild them.

The rule of thumb: *you are not allowed to leave a step until you can state a
concrete finding that justifies moving on.* "EDA looks clean" is not a finding.
"177 of 891 ages are missing and the missingness is 1.7x more common among
non-survivors, so imputation must be conditional" is a finding.

## Common failure modes

| Failure | Symptom | Where it goes wrong |
| --- | --- | --- |
| Jumping straight to modelling | Model fits, then fails in production | Steps 1-4 skipped |
| Target leakage | Unrealistic validation score | Step 5 |
| Peeking at the test set | Optimistic score, no real signal | Step 7 |
| Treating every missing value the same | Biased imputation | Step 4 |
| Optimising accuracy on imbalanced data | Model that only predicts the majority class | Step 7 |
| No baseline model | You cannot tell if your model is any good | Step 6 |
| Deploying without monitoring | Silent degradation | Step 8 |

The last two are the ones beginners skip most. A baseline is the cheapest possible
model (predict the majority class, or the mean) and it exists purely so that you
have a floor to beat. If your logistic regression scores 0.79 accuracy and
majority-class scores 0.61, you know something.

## Step 1 - Define the Problem

Clearly understand the business or research question, define the objectives, and
determine how success will be measured.

### What a problem statement must contain

Four things, written down before any code:

1. **The question** - one sentence, answerable.
2. **The target** - the exact column that will be predicted or explained.
3. **The unit of analysis** - one row of the dataset. This is where projects die:
   if one row is a "passenger booking" and a family shares a booking, your
   evaluation unit leaks across train and test.
4. **The success metric and its threshold** - a number, not a feeling.

### Bad vs. good

> **Bad:** "Analyse the Titanic dataset to find out what affected survival."

Unmeasurable, no target, no threshold, and it invites you to look at `Survived`
against every column and report whatever is significant.

> **Good:**
> *Question*: which passengers were more likely to survive the sinking of the
> Titanic, and can that be predicted for a passenger we have never seen?
> *Target*: `Survived` (0/1, 891 rows, 342 positive = 38.38% base rate).
> *Unit*: one passenger (`PassengerId` is unique across all 891 rows).
> *Metric*: ROC-AUC on a stratified 20% holdout, with a majority-class baseline
> of 0.50 AUC and a target of at least 0.80.
> *Non-goal*: individual fate prediction for named historical people.

Writing the non-goals matters as much as writing the goals. Without them scope
expands silently.

### Cost of being wrong

State it explicitly, because it determines how much effort each later step gets:

| Decision type | Example | Tolerance for error |
| --- | --- | --- |
| Reversible, cheap | Recommending a movie | High - just try more |
| Irreversible, cheap | Spam filter toggle | Medium - log misses |
| Irreversible, expensive | Denying a loan / a rescue allocation | Low - needs strong validation |

### Step 1 checklist

- [ ] Question fits on one line
- [ ] Target column identified and its class balance measured
- [ ] Unit of analysis stated, and uniqueness of its key verified
- [ ] Metric and numeric threshold agreed
- [ ] Non-goals listed
- [ ] Known biases in the source data written down (this pays off at step 4)

```python
# Verifying the target exists and is usable is still step 1 work.
import pandas as pd

t = pd.read_csv("Titanic-Dataset.csv")

print("rows:", len(t))
print("unique passenger ids:", t["PassengerId"].nunique())     # 891 == 891, key is valid
print("target dtype:", t["Survived"].dtype)                   # int64
print("base rate:", t["Survived"].mean().round(4))            # 0.3838
print(t["Survived"].value_counts(normalize=True).round(4))    # 0 0.6162 / 1 0.3838
```

A 38.38% base rate tells you accuracy alone is a misleading metric - see
[Step 7](#step-7---evaluation).

## Step 2 - Data Collection

Gather relevant data from reliable sources such as databases, APIs, files, surveys,
or web services. Ensure that the data is sufficient and appropriate for the
problem.

### Sources and their failure signatures

| Source | What you get | What breaks silently |
| --- | --- | --- |
| CSV / Excel file | Whatever was exported | Encoding, delimiter, merged header rows, formulas cached as values |
| JSON API | Nested, typed, documented | Pagination truncation, rate limits, schema drift between versions |
| SQL database | Clean, relational, large | Joins that fan out, `LEFT JOIN` nulls, timezone of stored timestamps |
| Web scraping | Anything you can see | Layout changes, missing values encoded as `""` or `"N/A"`, rate limits |
| Surveys | Exactly the fields asked for | Non-response bias, leading questions, recall error |
| Sensors / IoT | High volume, real-time | Calibration drift, gaps, duplicate timestamps |

### Collection checklist

- [ ] Source is documented: owner, refresh cadence, extraction timestamp
- [ ] Row count after extraction matches the expected count
- [ ] Time range of the data is what you think it is
- [ ] Encoding and delimiter are explicit
- [ ] Primary key is unique
- [ ] You know whether the file is the full extract or a sample

### Reading files defensively with pandas

```python
import pandas as pd

# Plain read - correct for a clean UTF-8, comma-delimited file.
a = pd.read_csv("globalAirQuality.csv")

# Being explicit costs nothing and documents the assumption.
a = pd.read_csv(
    "globalAirQuality.csv",
    encoding="utf-8",
    sep=",",
    header=0,
    parse_dates=["timestamp"],       # parse at load, not later
    dtype={"country": "category"},   # low-cardinality strings -> category
)

# Messy real-world file: skip preamble rows, coerce bad numbers to NaN.
sales = pd.read_csv(
    "quarterly_report.csv",
    skiprows=3,
    thousands=",",
    na_values=["", "N/A", "null", "-"],
    encoding="latin-1",              # older exports are often latin-1
)

print(a.shape)          # (18000, 15)
print(a["timestamp"].min(), "->", a["timestamp"].max())
# 2025-11-04 18:25:17.554219 -> 2025-11-19 17:25:17.554219
print(a["country"].nunique(), "countries,", a["city"].nunique(), "cities")
# 38 countries, 50 cities
```

`parse_dates` at load time is the habit worth forming. A `timestamp` column left
as `object` cannot be resampled, compared with `.dt`, or sorted meaningfully - you
only find out when the first resample throws.

### Is the data sufficient?

Check the four conditions before moving on:

```python
a = pd.read_csv("globalAirQuality.csv", parse_dates=["timestamp"])

print("rows:", len(a), "expected 18000")          # volume
print("cities:", a["city"].nunique(), "expected 50")
print("rows per city:", a.groupby("city").size().unique())   # [360] - balanced
print("span days:", (a["timestamp"].max() - a["timestamp"].min()).days + 1)  # 16
print("duplicate rows:", a.duplicated().sum())     # 0
print("fully-missing cells:", int(a.isna().sum().sum()))  # 0
```

All balanced here: 50 cities x 360 hourly readings = 18000 rows over 16 days. An
*unbalanced* panel is not automatically a problem, but you must know, because it
decides whether a naive mean over all rows is a fair city average. Here it is only
fair by luck - equal rows per city. In general, weight or aggregate first.

### Data collection is never finished

New rows arrive and the schema changes. `assert` a schema on the way in so the
failure is loud and immediate rather than a wrong number three steps later:

```python
EXPECTED = {"city", "aqi", "temperature", "humidity", "timestamp"}
missing = EXPECTED - set(a.columns)
assert not missing, f"schema drift: {sorted(missing)}"
```
